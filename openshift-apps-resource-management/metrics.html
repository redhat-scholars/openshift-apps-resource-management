Tailor metrics

Firstly, let’s add the micrometer extension to our setup. Please open a new terminal window, and make sure you’re at the root of your tutorial-app project, then run:

./mvnw quarkus:add-extension -Dextensions="io.quarkus:quarkus-micrometer,quarkus-micrometer-registry-prometheus"

Configuration of common tags

When deploying across multiple projects/namespaces it is always good to have a unified view over some application metrics. Let’s define several common tags for the application, varying in value at deployment time:

package com.redhat.developers;

import io.smallrye.config.ConfigMapping;

@ConfigMapping(prefix = "global")
interface GlobalTagsConfig {
     String PROFILE = "profile";
     String REGION = "region";
     String COUNTRY="country";

     String region();
     String country();
}

The @ConfigMapping(prefix = "global") annotation maps configurations from application.properties prefixed by global:

global.region=${REGION:CEE} (1)
global.country=${COUNTRY:Romania} (2)
1 Environment configuration will be named REGION and have the default value CEE.
2 Do not quote the default value. ${COUNTRY:'Romania'} makes the single quotes part of the value and every metric ends up tagged country="'Romania'".

Further, we will propagate these configurations via MeterFilter customization:

package com.redhat.developers;

import io.micrometer.core.instrument.Tag;
import io.micrometer.core.instrument.config.MeterFilter;
import io.quarkus.runtime.LaunchMode; (1)

import jakarta.enterprise.inject.Produces; (2)
import jakarta.inject.Inject;
import jakarta.inject.Singleton;
import java.util.Arrays;

@Singleton
public class CustomConfiguration {

    @Inject
    GlobalTagsConfig tagsConfig;

    @Produces
    @Singleton
    public MeterFilter configureTagsForAll() {
        return MeterFilter.commonTags(Arrays.asList(
           Tag.of(GlobalTagsConfig.REGION, tagsConfig.region()),
           Tag.of(GlobalTagsConfig.COUNTRY, tagsConfig.country()),
           Tag.of(GlobalTagsConfig.PROFILE, LaunchMode.current().getDefaultProfile()) (3)
        ));
    }

}
1 io.quarkus.runtime.configuration.ProfileManager was removed in Quarkus 3.
2 Quarkus 3 runs on Jakarta EE 10: every javax. import becomes jakarta..
3 LaunchMode.current().getDefaultProfile() is the replacement for ProfileManager.getActiveProfile().

Metrics definition at endpoint level

When looking to improve the performance of certain application features, it is useful to have metrics defined at endpoint level as well. Let’s modify GreetingResource with the following:

package com.redhat.developers;

import io.micrometer.core.annotation.Counted;
import io.micrometer.core.annotation.Timed;

import jakarta.transaction.Transactional;
import jakarta.ws.rs.*;
import jakarta.ws.rs.core.MediaType;
import java.util.List;

@Path("messages")
public class GreetingResource {

    public static final String URI = "uri";
    public static final String API_GREET = "api.greet";

    @POST
    @Produces(MediaType.APPLICATION_JSON)
    @Consumes(MediaType.APPLICATION_JSON)
    @Transactional
    @Timed(value = "greetings.creation", longTask = true, extraTags = {URI, API_GREET})(1)
    public Message create(Message message) {
        Message.persist(message);
        return message;
    }

    @GET
    @Produces(MediaType.APPLICATION_JSON)
    @Counted(value = "http.get.requests", extraTags = {URI, API_GREET})(2)
    public List<Message> findAll() {
        return Message.findAll().list();
    }

}
1 Measure expected long running requests with the @Timed annotation.
2 Count the creation of resources with the @Counted annotation.

Inspect the custom metrics

Start the application in DevMode:

./mvnw quarkus:dev

and curl the /messages endpoint a couple of times:

curl localhost:8080/messages

You can see your custom metrics recorded at http://localhost:8080/q/metrics :

jvm_memory_max_bytes{area="heap",country="Romania",id="G1 Eden Space",profile="dev",region="CEE"} -1.0
jvm_memory_max_bytes{area="heap",country="Romania",id="G1 Survivor Space",profile="dev",region="CEE"} -1.0
jvm_memory_max_bytes{area="heap",country="Romania",id="G1 Old Gen",profile="dev",region="CEE"} 8.334082048E9
jvm_memory_max_bytes{area="nonheap",country="Romania",id="CodeCache",profile="dev",region="CEE"} 5.0331648E7
jvm_memory_max_bytes{area="nonheap",country="Romania",id="Compressed Class Space",profile="dev",region="CEE"} 1.073741824E9
jvm_memory_max_bytes{area="nonheap",country="Romania",id="Metaspace",profile="dev",region="CEE"} -1.0
# HELP http_get_requests_total
# TYPE http_get_requests_total counter
http_get_requests_total{class="com.redhat.developers.GreetingResource",country="Romania",exception="none",method="findAll",profile="dev",region="CEE",result="success",uri="api.greet"} 3.0
The profile tag reads dev because you started the application with quarkus:dev. On JDK 21 the default garbage collector is G1, so the memory pool ids are G1 Eden Space / G1 Survivor Space / G1 Old Gen.

Deploy to OpenShift

You can deploy your latest code changes by using the command:

./mvnw clean package -Dquarkus.openshift.deploy=true -Dquarkus.container-image.push=true

However, we should externalize the configuration to OpenShift resources. Firstly, let’s create a configmap:

oc create cm country-nl --from-literal=region=Europe --from-literal=country=Netherlands

And we can append this new resource to our existing deployment:

oc set env --from=configmap/country-nl deployment/tutorial-app (1)
1 There is no DeploymentConfig any more — the Quarkus OpenShift extension generates an apps/v1 Deployment, named after the application. oc set env --from=configmap uppercases the ConfigMap keys, so region/country become the REGION/COUNTRY variables that ${REGION:CEE} and ${COUNTRY:Romania} expect.

Setting an environment variable already triggers a new rollout; wait for it to finish with:

oc rollout status deployment/tutorial-app

You can now check your overwritten metrics via:

export ROUTE_URL=https://$(kubectl get route tutorial-app -o jsonpath='{.spec.host}')
curl $ROUTE_URL/messages
curl $ROUTE_URL/q/metrics | grep http_get_requests_total
http_get_requests_total{class="com.redhat.developers.GreetingResource",country="Netherlands",exception="none",method="findAll",profile="prod",region="Europe",result="success",uri="api.greet"} 2.0

The region and country tags now carry the values coming from the ConfigMap, and profile is prod because the container runs a packaged application.
