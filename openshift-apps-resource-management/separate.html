Test configurations

In the previous examples we used the autogenerated files for deploying to Kubernetes/OpenShift. However, when moving towards a production environment it is unlikely for your deployments to be controlled only using those configurations.

A common practice is to create a dedicated folder for the Kubernetes/OpenShift YAML resources and leave the pipelines to customize those definitions upon interacting with a different namespace/project setup.

Let’s set up such a folder in src/main and name it k8s.

Integration tests to avoid problems

In this folder src/main/k8s add a deployment.yml file with the following content:

apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app.openshift.io/runtime: quarkus
    app.kubernetes.io/version: 1.0-SNAPSHOT
    app.kubernetes.io/name: greeting-app
  name: greeting-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app.kubernetes.io/version: 1.0-SNAPSHOT
      app.kubernetes.io/name: greeting-app
  template:
    metadata:
      labels:
        app.openshift.io/runtime: quarkus
        app.kubernetes.io/version: 1.0-SNAPSHOT
        app.kubernetes.io/name: greeting-app
    spec:
      containers: (1)
          image: quay.io/myrepo/greeting-app:1.0-SNAPSHOT
          imagePullPolicy: IfNotPresent
          name: greeting-app
          ports:
            - containerPort: 8080
              name: http
              protocol: TCP
          resources:
            limits:
              cpu: 500m
              memory: 400Mi
            requests:
              cpu: 100m
              memory: 256Mi
1 The deliberate mistake: containers is a list, but here it is written as a single mapping. This is the kind of typo that is easy to make by hand and painful to discover at deployment time.

Earlier revisions of this tutorial used a DeploymentConfig here. DeploymentConfig is deprecated since OpenShift 4.14 and the Quarkus OpenShift extension now generates a plain apps/v1 Deployment, so this chapter uses a Deployment too.

Typically you would install src/main/k8s/deployment.yml in an OpenShift environment and observe that the configuration is rejected. However, you can avoid reaching deployment time to realize that, by creating an integration test backed by the Kubernetes mock server.

Add the following two dependencies to your pom.xml:

    <dependency>
      <groupId>io.quarkus</groupId>
      <artifactId>quarkus-kubernetes-client</artifactId> (1)
    </dependency>
    <dependency>
      <groupId>io.quarkus</groupId>
      <artifactId>quarkus-test-kubernetes-client</artifactId> (2)
      <scope>test</scope>
    </dependency>
1 The mock server needs a real client implementation on the classpath. Without it the test fails with ClassNotFoundException: io.fabric8.kubernetes.client.impl.KubernetesClientImpl — the quarkus-openshift extension alone is not enough.
2 quarkus-test-openshift-client no longer exists in the Quarkus 3 BOM; quarkus-test-kubernetes-client is the only remaining mock-server artifact.

Now let’s create an integration test for the Deployment resource defined in the file:

package com.redhat.developers;

import io.quarkus.test.junit.QuarkusTest;
import io.quarkus.test.kubernetes.client.KubernetesServer;
import io.quarkus.test.kubernetes.client.KubernetesTestServer;
import io.quarkus.test.kubernetes.client.WithKubernetesTestServer;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.assertThrows;

@WithKubernetesTestServer (1)
@QuarkusTest
public class DeploymentFileTest {

    @KubernetesTestServer
    KubernetesServer mockServer; (2)

    @Test
    public void testDeploymentFile() {
        String pathToDeployment = "./src/main/k8s/deployment.yml"; (3)
        RuntimeException thrown = assertThrows(IllegalArgumentException.class, (4)
                () -> mockServer.getClient().apps().deployments().load(pathToDeployment).dryRun());
        System.out.println("Rejected manifest: " + thrown.getMessage());
    }

}
1 Annotate the test so that a mock Kubernetes API server is started for it.
2 Inject the mock server. Note the type is io.quarkus.test.kubernetes.client.KubernetesServer, not fabric8’s KubernetesMockServer — and fabric8 7.x removed io.fabric8.kubernetes.client.server.mock.KubernetesServer altogether.
3 Specify the path to the resource under test.
4 Dry run the installation of the resource present in the file. Deserialization now fails before the request is sent, so the exception is an IllegalArgumentException, not a KubernetesClientException.

By running the test (via Continuous Testing / IDE / ./mvnw test) you will get an exception that also tells you what is wrong with the resource:

Rejected manifest: Cannot deserialize value of type `java.util.ArrayList<io.fabric8.kubernetes.api.model.Container>` from Object value (token `JsonToken.START_OBJECT`)
 at [Source: UNKNOWN; byte offset: #UNKNOWN] (through reference chain: io.fabric8.kubernetes.api.model.apps.Deployment["spec"]->io.fabric8.kubernetes.api.model.apps.DeploymentSpec["template"]->io.fabric8.kubernetes.api.model.PodSpec["containers"])

Fixing the manifest is then a one-character change — turning the containers mapping into a list by prefixing image: with `- `.
